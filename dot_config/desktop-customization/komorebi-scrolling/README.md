# Горизонтальный Scrolling: проба и возврат BSP

Подготовлено 24 октября 2026 года для HOMEPC, komorebi 0.1.41.
Ветка dotfiles `komorebi-scrolling` ответвлена от `yasb-catppuccin` (`593f303`).
27 октября 2026 Scrolling реально включён на пространстве 1. После подтверждённой
пробы одного широкого окна включены две видимые колонки с краями соседей. Пространства 2–9 остаются BSP. Сохранённый komorebi.json
по-прежнему содержит девять BSP. Владелец подтвердил расположение окон в ленте,
но счёл клавиатурное переключение неудобным и попросил мышь/колёсико.
YASB, komorebi/whkd, ScriptLauncher и автозапуск ради этого не перезапускались.
Для новой привязки обновлён и перезапущен только существующий DesktopBridge.

## Как попробовать и вернуть

1. Перейти на нужное пространство, например Alt+9 для отдельной пробы.
2. Запустить `Scrolling.cmd` из этой папки. Меняется только это пространство:
   горизонтальная лента с одним широким окном и соседними краями. Открыть несколько окон,
   закрыть окно Проводника/терминала, если оно мешает оценке.
3. Alt+H / Alt+L — переход между окнами влево/вправо; Alt+Shift+H/L — перемещение
   окна. Alt+1…9 — прежнее переключение пространств. Визуальное поведение этих
   действий в Scrolling ещё предстоит проверить на твоих приложениях.
4. На том же пространстве запустить `BSP.cmd` — вернуть BSP без перезапуска
   менеджера, темы или AHK. Повторить для каждого пространства, где пробовал.

Можно закрепить папку в быстром доступе Проводника или создать ярлыки на эти два
файла в меню «Пуск». Автозапуск и новые горячие клавиши намеренно не добавлялись.
`Status.cmd` показывает текущие монитор, пространство и раскладку.
Скрипты не закрывают приложения; восстановление прежнего расположения каждого
окна пиксель в пиксель не обещается — BSP пересчитает размещение.

## Управление колёсиком в экспериментальной ветке

**Alt + колёсико над окном**: вверх — предыдущее окно, вниз — следующее.
Alt + горизонтальное колёсико также поддержан. Обычная прокрутка сохраняется.
Работает только в Scrolling на одном мониторе, над управляемым окном,
без дополнительных Ctrl/Shift/Win и без инъекционных mouse events.
Полноэкранное окно, monocle/maximized, пауза WM и активная игровая блокировка
ScriptLauncher отключают перехват. После возврата BSP hook снимается.

Привязку обслуживает существующий DesktopBridge, без AHK или нового daemon.
Поток Windows обрабатывает hook; команды komorebic выполняются отдельно с
таймаутом 2 секунды и повторной проверкой пространства/foreground. Ограничение
частоты — один шаг за 120 ms; высокий resolution колёсика суммируется до шага.
ScriptLauncher проверяется по живому PID/пути текущей сессии и status.json:
игровые блокировки учитываются, ручное выключение AHK не отменяется. Heartbeat
обновляется раз в 15 секунд; статус старше 45 секунд отключает привязку.
Подробности последнего действия без заголовков окон — runtime/scroll-input.json.

## Терминал и проверка без применения

Из PowerShell в этой папке:

```powershell
.\Switch-Layout.ps1 -Mode Scrolling -WhatIf
.\Switch-Layout.ps1 -Mode Scrolling -Columns 1 -Peek 180
# Прежние две полные колонки, без предпросмотра краёв:
.\Switch-Layout.ps1 -Mode Scrolling -Columns 2 -Peek 0
.\Switch-Layout.ps1 -Mode Bsp
.\Switch-Layout.ps1 -Mode Status
```

`-WhatIf` читает состояние и показывает план без изменения раскладки.
Команды используют действующую пользовательскую сессию и установленный
komorebic; права администратора, отдельный WM и AHK им не нужны.
При ошибке IPC скрипт останавливается: не трогает runtime junction и процессы.
При нескольких мониторах включение Scrolling блокируется; возврат BSP доступен.
Сначала закончить тест и вернуть BSP, затем подключать дополнительный монитор.

## Что сохраняется

Переключение временное: `komorebi.json` остаётся с девятью BSP. Перезагрузка
конфига (Alt+Shift+O) или перезапуск менеджера должны снова применить сохранённый
BSP. Для обычного возврата удобнее `BSP.cmd`; откат всей темы не требуется.
Не нажимать Apply/Restore темы ради смены раскладки.

Ветка Git хранит код, **сама по себе не переключает рабочий стол**.
Исходники: `dot_config/desktop-customization/komorebi-scrolling/` в dotfiles;
chezmoi включает папку только в Windows desktop-профиле. На новой машине после
просмотра diff можно применить только эту папку; глобальный apply ради неё
не нужен. Постоянный Scrolling и меню выбора в YASB — следующий этап после
ручной пробы. Нынешний BSP-виджет YASB не является новым переключателем:
его прежний клик monocle сохранён, отдельная иконка Scrolling ещё не добавлена.

## Проверено и ограничения

Проверены наличие CLI-команд в установленной версии, синтаксис PowerShell,
чтение состояния и план `-WhatIf`. В момент подготовки: один монитор, девять BSP.
27 октября runtime state подтвердил Scrolling только на первом пространстве;
конфиги и PID WM/whkd/YASB/ScriptLauncher сохранены. Владелец подтвердил ленту.
Плавность, разные приложения, реальные игры и несколько мониторов не проверены.
Mouse policy/parser tests и native hook probe прошли: настоящий hook ставится
и снимается при тестовой игровой блокировке, весь реальный ввод пропускается
за счёт пустого списка HWND. Это не проверка античита реальной игры.

Встроенный Scrolling — горизонтальная раскладка komorebi, не полная копия niri
с его жестами и обзором. Другие менеджеры пока не устанавливались.

Источники: [раскладки и переключение](https://komorebi.lgug2z.com/usage/layouts/),
[число колонок](https://lgug2z.github.io/komorebi/cli/scrolling-layout-columns.html),
[ограничение одним монитором](https://komorebi.lgug2z.com/guides/known-issues/).

27 октября владелец физически подтвердил: Alt+колёсико переключает окна ленты,
управление стало удобным. AHK остались выключены; профильные конфиги сохранены.

## Края соседних окон — подтверждённая проба 27 октября

Scrolling.cmd теперь выбирает Columns=1, Peek=180. Штатный workspace offset
равен left=180, top=0, right=360, bottom=0 при исходных нулевых отступах.
В Rect komorebi right — поправка ширины: удвоенный left даёт симметричные поля.
На экране 2560 px центральное окно шириной 2164 px, видимый соседний край
около 178 px с учётом padding. В середине ленты видны оба соседа; на краях
ленты с одной стороны соседа нет. Владелец подтвердил именно желаемый вид.
Нативное центрирование center_focused_column для этой пробы не меняли.

Новый Switch-Layout сохраняет прежние эффективные workspace offsets в локальный
runtime/layout-offsets.json, отдельно для устройства/пространства. Повторное
включение не накапливает отступы. BSP.cmd и Scrolling с Peek=0 восстанавливают
прежнюю геометрию и снимают запись. CLI восстанавливает унаследованный null
как эквивалентный эффективный Rect (здесь нули); файл komorebi.json не меняется.
WhatIf не создаёт runtime; ошибка переключения возвращает BSP и прежние offsets.
Проверено 12 isolated assertions: WhatIf, идемпотентность, сохранение собственных
отступов, возврат BSP, сбой columns и возврат двух колонок. Реальных WM-команд
в этом тесте не было; фактические края подтверждены отдельно владельцем.

## Приближение к LeopardWM, 27 октября 2026

Выбран именно komorebi: смены менеджера нет. Проба на пространстве 1:
Scrolling, Columns=2, Peek=180; пространства 2–9 BSP. Существующие ручные
resize_dimensions и размеры окон сохраняются, переключатель их не сбрасывает.
Базовая сетка равная, но ручные изменения ширины делают окна разными.

Правый клик по ↻ → **Лента окон**:

- **Одно широкое окно** — Columns=1/Peek=180.
- **Два окна рядом** — Columns=2/Peek=180. При ручных изменениях ширины два
  окна могут перестать помещаться целиком; режим не сбрасывает эти изменения.
- **Вернуть BSP** — прежняя раскладка и эффективные боковые отступы.
- **Плавное движение (все пространства)** — нативная movement-анимация:
  160 ms, ease-out-cubic, 60 fps. Это глобальная настройка сессии, затрагивает
  и BSP; прозрачность окон не включается. Не утверждаем DwmFlush/vsync как у LeopardWM.
- **Без анимации** — выключить movement-анимацию. BSP меняет только раскладку,
  поэтому при необходимости отдельно выключить анимацию этим пунктом.

Без меню: Scrolling.cmd — одно окно, Scrolling-Two.cmd — два, BSP.cmd — возврат.
Set-Motion.ps1 -Mode Smooth / Instant управляет только анимацией; поддержан WhatIf.
Исходный постоянный конфиг не задаёт анимацию; Instant соответствует его
визуальному поведению. Прежние произвольные временные параметры анимации CLI
не раскрывает: точное восстановление их значений не обещается.

Управление остаётся привычным:

- Alt+колёсико — соседнее окно и необходимая прокрутка; обычное колесо — приложение.
- Клик по видимой части соседнего окна — обычная активация окна.
- Alt+плюс/минус — ширина; Alt+Shift+H/L — порядок окон.
- Alt+Shift+F — временный monocle, повторить для возврата ленты; Alt+T — floating.
- Alt+1…9 — пространства. Новых F-клавиш, AHK и фоновых процессов не добавлено.

В этой версии Scrolling выбирает положение viewport по равной базовой сетке,
затем применяет ручные размеры. Поэтому это не точная копия независимых ширин
и камеры LeopardWM: при сильном расширении окно может обрезаться. Свободное
смещение камеры в пикселях без изменения фокуса и обзор всех пространств
штатными командами здесь не добавлены. Focus-follows-mouse, системные параметры
Windows, игровые правила и постоянный komorebi.json не меняются.

Меню использует существующий DesktopBridge и кратковременный Services.ps1.
Изменения профиля не вызывают RestartAll/перезапуск WM; AHK остаётся под прежним
ScriptLauncher. После перезапуска WM временные режимы нужно включить снова.

## Требование владельца и результат оценки

Владелец сообщил, что переключение пресетов неудобно. Цель уточнена:
произвольная ширина каждой колонки, вся полоса не обязана помещаться на экран;
изменение ширины пересчитывает полосу, а несколько одновременно видимых окон
друг над другом составляют одну колонку и прокручиваются вместе.
Удобство нового меню/анимации не подтверждено, пресеты эту цель не реализуют.

Проверены arrangement.rs и container.rs тега v0.1.41 (27 октября 2026).
Scrolling рассчитывает viewport по базовым равным колонкам до применения
resize_dimensions. Container::load_focused_window скрывает остальных участников
stack, так что stack не заменяет вертикальную колонку с несколькими видимыми
окнами. В просмотренной ветке master расчёт Scrolling также совпадает.
Поэтому полная цель выходит за выбранные рамки настройки штатного komorebi.

Для экспериментальной доработки потребуются: модель колонки с собственной
шириной и вертикальными дочерними окнами; размещение по накопленным фактическим
ширинам; viewport с обеспечением видимости фокуса; изменения resize, focus,
переноса/объединения/разделения и сохранения колонок. Отдельная проверка нужна
для закрытия окон, диалогов, восстановления сессии, DPI и совместимости YASB.
Это ещё не реализовано; сборки/патча ядра и нового менеджера здесь нет.
