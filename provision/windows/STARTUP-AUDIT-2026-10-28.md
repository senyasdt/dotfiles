# Аудит входа Windows: 28 октября 2026

Запрос владельца: убрать рывки и ожидание 2–3 минуты после входа. Проверены
обычный пользовательский реестр через WMI, Startup обоих уровней, packaged
StartupTasks, 202 задачи, 302 службы и 473 драйвера. Raw inventory, команды,
SID, логи, XML задач и резервные копии оставлены локально вне Git.

## Что обнаружено

- Win32 StartupCommand содержал 22 записи: пользовательские и машинные Run,
  четыре файла Startup. Дополнительно шесть packaged StartupTasks были включены.
- Службы и оболочка появлялись примерно через 27 s от старта ОС. Затем в первые
  две минуты запускались игровые лаунчеры с дочерними web-процессами, два разных
  Яндекс.Диска, фоновый Яндекс.Браузер, Flow, PowerToys и Codex.
- Нативный AHK guard появился примерно через 106 s от старта ОС, ZMK — через
  124 s. Это историческая последовательность процессов текущего входа, а не
  измерение полного времени готовности или CPU-пиков каждой программы.
- Одновременно были зарегистрированы Vial Helper Daemon, старый Python Vial
  Layer Daemon и Startup wrapper. cute-borders запускался поверх собственных
  рамок LeopardWM. YASB имел отдельную задачу помимо общего запуска.
- MSIX перенаправляет часть реестра и AppData процесса Codex. Например, обычное
  чтение HKCU показывало три пользовательских Run, реальный hive — четырнадцать.
  Поэтому для изменений использован системный StdRegProv, для проверки — задачи
  Планировщика, запущенные в обычном пользовательском контексте.
- Общий Startup пуст, кроме desktop.ini. Shell/Userinit/BootExecute штатные.
  Найден стандартный WMI SCM Event Log Filter; исполняемых WMI consumers не найдено.
- Политика системных служб, драйверов, Defender, VPN и аппаратных утилит сохранена.

## Применённый порядок

Задержки отсчитываются **от входа пользователя**, не от разблокировки и не от
готовности предыдущей программы. Их выполняет Планировщик; ожидающих PowerShell
процессов и нового постоянного watchdog нет. Все новые задачи работают с обычными
правами пользователя.

| Когда | Что |
| --- | --- |
| +1 s | Desktop Session: AHK guard, выбранный WM, YASB + DesktopBridge, Vial/ZMK при наличии |
| +40 s | Яндекс.Диск 4 |
| +60 s | OneDrive |
| +90 s | Codex через стабильный AppsFolder ID |
| +120 s | Существующая UpdateTorrent: сохранены действие, пользователь и прежний уровень прав |

По ответам владельца Steam, EA и SeleZen переведены на ручной запуск. Сохранён
Яндекс.Диск 4; прежний Диск 3 исключён из входа. Microsoft 365/Files/Copilot,
обе версии Teams и фоновый Яндекс.Браузер тоже запускаются вручную. Старый
MyDockFinder удалён из Run. Текущие приложения и синхронизации принудительно
не закрывались: новая политика действует при следующих входах.

Взамен четырёх старых файлов Startup установлена ранняя задача Desktop Session.
Задачи cute-borders, старого Python Vial, отдельного Vial wrapper и YASB отключены.
Остановлены только старые рамки и Python Vial; работающая панель и нативные HID
помощники сохранились. Игровые блокировки и ручные состояния AHK не менялись.
PowerToys, Flow, периферийные утилиты и CrossDevice оставлены доступными.

Последующее уточнение владельца: AHK должны включаться при каждом новом входе.
В `desktop.json` добавлен `enableAhkOnLogin: true`. Команда guard `--login all`
однократно включает все настроенные скрипты по идентификатору загрузки и Windows
AuthenticationId. Маркер сохраняется в private runtime. Повторный запуск в том
же входе, включая перезапуск guard, сохраняет ручной OFF. Игры и задержка после
них по-прежнему блокируют запуск. Для возврата прежнего поведения поставить
`enableAhkOnLogin: false`.

## Проверка и границы результата

Дополнение 29 октября: после выхода из Apex осталась стандартная US-раскладка.
Отдельный TechnicalAltGrLayoutGuard не работал, его записи в обычном Run не было;
последний старый лог датировался 24 октября. Ручной запуск сразу удалил 04090409,
сохранив F0010409 и F0020419. Помощник перенесён в desktop-customization и включён
через `startLayoutGuard: true` в общей Desktop Session. Повторный запуск сохранил
PID; проверочный запуск задачи завершился кодом 0. Холодный вход ещё не проверен.
На новой машине он остаётся opt-in: нужны обе кастомные раскладки и установка
с `-IncludeLayoutGuard`; обычное восстановление desktop.json выключает эту опцию.

- Проверочный старт через новую задачу завершился с кодом 0: вся последовательность
  проверки уже работающих компонентов заняла около 1,9 s. В логе есть длительность
  каждого компонента. Это **не измерение холодного входа**.
- Каждая из трёх отложенных задач проверена вручную. Код 0, существующие PID
  приложений сохранились, дополнительные экземпляры не появились.
- Реальный Run и packaged States повторно прочитаны через WMI. Старые задачи
  отключены; у YASB текущий экземпляр задачи может показываться Running, хотя
  Settings.Enabled уже false — активная панель остаётся открыта.
- Журнал Diagnostics-Performance уже был включён. Событий 100–103 за последние
  три дня не получено даже с правами администратора. Нельзя честно назвать
  выигрыш в секундах до повторного входа/перезагрузки.
- Проверены PS5.1/PS7, парсинг команд, защита от конкурентного изменения реестра,
  восстановление значений, владение процессами, текущие задачи и launcher.
  Полный системный откат на рабочем ПК не выполнялся, чтобы не возвращать нагрузку.

## Воспроизведение и откат

Файлы находятся в `dot_config/desktop-customization/startup/`; настройки —
`policy.json`. Локальный runtime содержит только вычисленные пути приложений,
backup marker и логи, не переносимые на новый компьютер.

После обычного restore окружения отдельно просмотреть эту политику:

```powershell
# Только план; Root по умолчанию: ~/.config/desktop-customization
& "$src\provision\windows\Optimize-Startup.ps1" -Action Plan
# Применение из терминала с правами администратора того же владельца:
& "$src\provision\windows\Optimize-Startup.ps1" -Action Apply
# Состояние и возвращённые сторонними приложениями записи:
& "$src\provision\windows\Optimize-Startup.ps1" -Action Status
```

На HOMEPC передать `-Root "$env:USERPROFILE\WorkingFolder\desktop-customization"`.
Apply сохраняет исходные значения реестра, XML задач и файлы Startup. При ошибке
пытается выполнить обратные изменения. Rollback предварительно проверяет владельцев
и сохранность значений, не перезаписывает обнаруженные сторонние изменения.

```powershell
& "$src\provision\windows\Optimize-Startup.ps1" -Action Rollback `
  -Root "$env:USERPROFILE\WorkingFolder\desktop-customization" `
  -BackupDirectory "$env:USERPROFILE\WorkingFolder\desktop-customization\backup\startup-policy-20261028"
```

Для изменения уже установленной политики сначала Status, затем явный Rollback
нужной резервной копии и новый Plan/Apply. Повторная Apply не создаёт дубли:
она отказывается заменять уже существующие задачи. Restore/Apply оформления
распознают установленную задачу и не создают второй Startup-ярлык.

Задержки и исключения — пользовательский выбор, не универсальный системный твик.
На новом ПК отсутствующие приложения пропускаются. Нативные установщики/обновления
могут повторно зарегистрировать свой автозапуск; Status показывает такое расхождение.
